# stage-7-release

## Контекст

<!-- Context -->

Етапи 1–6 заархівовані: сервіс приймає вебхуки, генерує чернетки, дає оператору модерувати й надсилає відповіді.
ROADMAP етапу 7 вимагає навантажувальний прогін (500 подій, 20% дублів, паралельність 50, p99 < 2 с), README, зведення рішень і (бажано) деплой.
Ця зміна доповнює [`webhook-sender`](/dev/specs/webhook-sender/spec.md) і в решті — документація та конфігурація.

## Мета

**Цілі:**
<!-- Goals -->

- Числа навантажувального прогону (всі унікальні `event_id` у БД, 0 дублів, p99) зафіксовано в README.
- Людина за README запускає сервіс, налаштовує LLM, проганяє тести й скрипт і розуміє ключові рішення.
- `docker-compose.yml` безпечний для VPS.

**Поза межами зміни:**
<!-- Non-Goals -->

- Сам деплой і публічні посилання: потрібні обліковий запис хостингу й API-ключ користувача; README містить інструкцію.
- Перевірка «чиста машина» — користувач виключив її з тесту.
- Покращення зі звітів верифікації (очищення `last_error`, ліміти полів тощо) — у README в розділі «Що далі».

## Рішення

<!-- Decisions -->

**Затримки в `scripts/send_webhooks.py`.**
`send_all` повертає `(Counter, list[float])` — лічильник статусів і тривалості успішно отриманих відповідей (`time.perf_counter()` навколо `client.post`).
`latency_summary(durations) -> str | None`: `None` для порожнього списку, інакше `latency ms: p50=… p99=… max=…` (цілі мс) через `statistics.quantiles(durations, n=100, method="inclusive")`; для одного виміру всі три дорівнюють йому.
`main()` друкує рядок, якщо він не `None`.
Тести, що вже викликають `send_all`, переходять на нову форму результату.

**Порт БД — лише локально.**
`"127.0.0.1:${DB_PORT:-5432}:5432"`: тести з хоста працюють як раніше, з мережі база недоступна.

**Навантажувальний прогін.**
Стек у режимі без ключа зі `STUB_DELAY_*=0` (вебхук від LLM не залежить, а черга генерації швидко спорожніє), чиста таблиця `tickets`, команда з ROADMAP:
`uv run python -m scripts.send_webhooks --count 500 --dup-rate 0.2 --concurrency 50`.
Перевірки: вивід скрипта (`sent: 600`, `202: 600`, рядок затримок) і SQL — `count(*) = 500`, `count(distinct event_id) = 500`.
Результати — у README, розділ «Навантажувальний прогін».

**README.md** (українською), розділи: що це; архітектура (Mermaid-схема з розділу 2 ROADMAP + стейт-машина статусів); швидкий старт; налаштування LLM (Ollama на хості з `LLM_REASONING_EFFORT`, Groq/Gemini/OpenRouter, режим без ключа); змінні оточення (таблиця); UI оператора й мок хелпдеску; тести; навантажувальний скрипт і результати; ключові рішення й компроміси (черга в Postgres, ідемпотентність, exactly-once лише з ключами хелпдеску, in-process лімітер, мок у пам'яті); деплой на VPS; що далі.

**`docs/decisions.md`** отримує вступ і короткий зміст за етапами; записи етапів лишаються як є.

## Ризики та компроміси

<!-- Risks and Trade-offs -->

- Прогін на ноутбуці міряє затримку разом із клієнтом на тій самій машині: це верхня межа, а не чистий час сервера; для ROADMAP (< 2 с) достатньо.
- Режим без ключа в прогоні не навантажує справжній LLM: пропускна здатність генерації обмежена провайдером і `LLM_RPM`, що описано в README як окреме обмеження.
